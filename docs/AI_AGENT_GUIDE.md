You are contributing to **ORACLY**.

ORACLY is not a tarot application.

It is a **premium digital sanctuary for reflection**.

When in doubt, defer to the Master Directive and Development Charter. This guide is the **daily decision layer** for agents writing code.

---

## Before every change ask

| Question | Required to proceed |
|----------|---------------------|
| Does this make the experience **calmer**? | Yes |
| Does this **increase trust**? | Yes |
| Does this improve **clarity**? | Yes |
| Does this **respect the user's intelligence**? | Yes |
| Does this fit the existing **ORACLY identity**? | Yes |

**If any answer is no — do not implement it.**

---

## Never

- Add unnecessary animations
- Introduce a second design language
- Duplicate components
- Rewrite stable systems
- Add complexity for visual impact
- Ship major image assets that look illustrated, vector, cartoon, plastic CGI, or like a cheap fortune-app mockup — see [Global Visual Quality System](./GLOBAL_VISUAL_QUALITY_SYSTEM.md) and [Photorealistic Art Standard](./PHOTOREALISTIC_ART_STANDARD.md)
- Put UI text, logos, or feature names inside generated images

---

## Always

- Reuse existing systems
- Keep code maintainable
- Keep animations subtle
- Prefer consistency over novelty
- Respect performance
- Respect accessibility
- Generate major artwork as photorealistic cinematic editorial stills (shared light/gold/violet DNA; feature-specific subjects)
---

## Emotional goal

Users should **never feel manipulated**.

They should feel:

- **Calm**
- **Curious**
- **Respected**
- **Present**

---

## Design goal

The interface should **disappear**.

The experience should **remain**.

---

## Engineering goal

Future developers should **immediately understand** the codebase.

Read before writing. Extend before creating. Split before bloating.

---

## Final rule

If your implementation makes ORACLY feel **more intentional** — continue.

If it only makes ORACLY **different** — stop and rethink.
